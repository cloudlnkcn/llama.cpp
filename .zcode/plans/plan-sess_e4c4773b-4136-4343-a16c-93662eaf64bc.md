## 修复 SYCL 包漏带 Unified Runtime adapter 和 oneTBB

### 根因(已在你机器上验证坐实)
`release.yml` 的 `Bundle SYCL runtime libraries` step 用 `ldd` 自动发现依赖,但有两类**间接依赖** `ldd` 结构上抓不到:

1. **`libur_adapter_*.so`(Unified Runtime adapter)** — `libur_loader.so` 在运行时 `dlopen` 它,没有任何 `.so` 直接 `NEEDED` 它,所以 `ldd` 列不出来。没有它,SYCL 枚举不到任何 GPU → 后端 init 抛 "No device of requested type available" → 被静默跳过 → `--list-devices` 返回 `(none)` → 模型全跑 CPU。这正是你之前看到的现象。
2. **`libtbb.so.12` / `libtbbbind_*.so`**(oneAPI oneTBB)— `libmkl_tbb_thread.so` 的间接依赖。系统的 `libtbb12` 能被 `ldd` 解析(所以不报 not found),但 ABI 与 oneAPI MKL 编译用的 oneTBB 不完全匹配 → `dlopen libggml-sycl.so` 时 `undefined symbol: _ZN3tbb6detail2r1...get_thread_reference_vertex...` → 后端加载失败。

### 改动(单文件:`/home/user/src/llama.cpp/.github/workflows/release.yml`)

**改动 1 — `Bundle SYCL runtime libraries` step(约 693 行 `done` 之后插入)**
在现有 `ldd` 自动发现循环之后,显式补抓 `ldd` 看不到的两类间接依赖。用 `find /opt/intel/oneapi ... -exec cp -aL` 解引用符号链接,与现有 `cp -aL` 风格一致:
- `libur_adapter_*.so*`(UR adapter,GPU 枚举的硬依赖)
- `libtbb.so*`、`libtbbbind*.so*`(oneAPI oneTBB,MKL TBB threading 的正确 ABI)

加注释说明"为什么 ldd 抓不到这两类"(loader 运行时 dlopen 的 adapter、ABI 敏感的 TBB),避免以后有人当成冗余删掉。

**改动 2 — `Validate SYCL package contents` step(约 718 行必需库检查之后插入)**
增加存在性断言作为回归防线(成本极低,但能防止 oneAPI 路径变化时再次漏带):
- 断言 `libur_adapter_level_zero.so*` 存在(没有它,GPU 100% 不可用)
- 断言 `libtbb.so*` 存在

### 不改动 / 保持现状
- 现有 `ldd` 自动发现逻辑保留(它抓 libsycl/libomp/libsvml/libmkl 等**直接**依赖是对的,只是补不全间接依赖)
- 现有"无 GPU runner 上把 `libggml-sycl.so` 改名绕过异常再跑 `--version`"的 smoke test 保留——CI runner 无 Intel GPU,无法真正跑通 SYCL 后端
- Intel GPU **内核驱动**仍由用户系统提供,不打包(保持现有行为);我们补抓的是**用户态** UR adapter,属 oneAPI 范畴,不冲突

### 不做更强的验证(及原因)
现有 `ldd` 检查测不出 `undefined symbol`(那是运行时 lazy binding 的事,这正是 TBB 问题漏网的原因)。可以加 `LD_BIND_NOW=1 ldd` 做符号检查,但 sycl 后端依赖链复杂、在无 GPU 环境易误报,且 CI 上无法端到端验证 GPU 枚举。因此用"关键文件存在性断言"做回归防线,保持改动聚焦、风险可控。
